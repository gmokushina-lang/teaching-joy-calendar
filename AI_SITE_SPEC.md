# Техническое задание для ИИ: календарь учителя Neo Kingdom

## 1. Роль ИИ и конечный результат

Ты — senior full-stack разработчик, UX/UI-дизайнер и специалист по Firebase. Создай готовое к запуску русскоязычное веб-приложение для частного учителя. Приложение позволяет учителю, ученику или родителю бронировать индивидуальные уроки; показывает владельцу абонемента его оставшиеся занятия; даёт учителю админ-панель для управления расписанием, оплатой, посещением и отчётами об уроках.

Работай итерациями, но не оставляй критические функции в виде заглушек. После каждой итерации запускай проверки и кратко объясняй владельцу проекта простыми словами, что сделано и как это проверить. Не требуй от владельца знания терминала или Firebase.

Результат должен включать:

- исходный код в GitHub-репозитории;
- адаптивный сайт на Firebase Hosting;
- Firebase Authentication, Cloud Firestore и Cloud Functions;
- безопасные Firestore Rules и Storage Rules;
- демонстрационные данные и отдельный безопасный скрипт их заполнения;
- README с пошаговым запуском и публикацией;
- тесты ключевой бизнес-логики и правил доступа.

Он не должен занимать весь первый экран или мешать работе с календарём. Используй `object-fit: cover`, адаптивную точку фокуса, затемняющий градиент и хороший контраст текста.

Визуальный язык: тёплый янтарный свет, дерево, бумага, карты и гирлянды из левой части референса; неоновый фиолетовый и голубой замок из правой части; ощущение уютной мастерской и сказочного цифрового королевства. Интерфейс должен оставаться спокойным, читаемым и рабочим, а не выглядеть как перегруженная игра.

## 3. Пользователи и роли

Роли:

- `admin` — учитель и единственный администратор;
- `student` — ученик;
- `parent` — родитель или законный представитель.

Один родитель может быть связан с одним или несколькими учениками. Ученик может иметь собственный вход. Родитель и ученик видят только собственные данные и уроки связанных учеников. Они никогда не должны видеть имена, контакты, комментарии, статусы оплаты или уроки других клиентов.

Урок может создать администратор, ученик или связанный с учеником родитель. Бронирование сразу получает статус `confirmed`; ручное подтверждение не требуется.

Для разработки создай демонстрационные аккаунты, например `teacher.demo@example.com`, `parent.demo@example.com`, `student.demo@example.com`. Пароли нельзя записывать в репозиторий, frontend-код, MD-файлы или историю Git. Скрипт seed должен получать временные пароли через переменные окружения либо предлагать установить их интерактивно. В production администратор меняет пароль и включает MFA, если она доступна.

## 4. Основные экраны

### 4.1. Вход и восстановление доступа

- вход по email и паролю через Firebase Authentication;
- восстановление пароля;
- понятные русские сообщения об ошибках;
- регистрация клиентов только по приглашению администратора либо через контролируемый процесс, исключающий самостоятельное получение роли `admin`;
- роль определяется сервером через custom claims или защищённый профиль, а не параметром из формы.

### 4.2. Календарь

Desktop и планшет показывают весь месяц на одном экране календарной области: 7 колонок, 5–6 строк недель, дни соседних месяцев приглушены. Нельзя заменять месяц бесконечным списком.

Телефон по умолчанию показывает неделю. Должны быть кнопки предыдущей и следующей недели, кнопка «Сегодня» и понятный заголовок диапазона дат. Месячный режим на телефоне необязателен.

Обязательные элементы:

- кнопки предыдущего и следующего месяца;
- кнопка «Сегодня»;
- текущий месяц и год;
- текущее время в выбранном пользователем часовом поясе;
- отдельное фиксированное время «МСК» (`Europe/Moscow`);
- кнопки ← и → рядом с выбранным временем для изменения часового пояса;
- после изменения пояса все даты и часы уроков пересчитываются для отображения, но исходный момент события не изменяется;
- подпись выбранного пояса, например `Europe/Moscow · UTC+3`, а не только неоднозначное `GMT+3`;
- настройка пояса сохраняется в профиле пользователя;
- свободные интервалы для бронирования и собственные уроки;
- для клиента занятые чужими учениками интервалы показываются только как «Недоступно» или вообще исключаются — без любых персональных сведений;
- легенда статусов и доступные с клавиатуры подсказки.

Время хранить в Firestore как UTC `Timestamp`. Для вычислений использовать IANA timezone и библиотеку с корректной поддержкой переходов летнего времени, например Luxon или date-fns-tz. Не хранить время только строкой и не прибавлять часы вручную.

### 4.3. Бронирование

Пользователь выбирает свободный интервал, связанного ученика, продолжительность из разрешённых вариантов и необязательный комментарий. Перед записью показать локальное время и время МСК. После сохранения урок сразу подтверждён.

Создание брони должно выполняться серверной транзакцией/Callable Function:

1. повторно проверить авторизацию и связь пользователя с учеником;
2. проверить рабочие часы и отсутствие блокировки;
3. проверить отсутствие пересечения с другим событием;
4. проверить, что дата не в прошлом;
5. проверить активность абонемента или разрешить разовое занятие;
6. создать событие и запись аудита атомарно.

Нельзя полагаться только на проверку в браузере: два пользователя могут одновременно выбрать один слот.

### 4.4. Повторяющиеся уроки

Администратор создаёт ученика или группу данных, но на первом этапе фактические занятия индивидуальные. Можно создать еженедельную серию: день недели, время, длительность, дата начала и дата окончания или число повторений.

Поддержать операции:

- изменить/удалить только выбранный урок;
- изменить/удалить выбранный и все последующие;
- изменить/удалить всю серию.

Удаление одного экземпляра не удаляет шаблон. Используй модель серии плюс исключения или материализованные экземпляры с `seriesId` и операциями над диапазоном. Сохраняй audit trail. Уже проведённые уроки нельзя молча переписывать при изменении серии.

### 4.5. Личный кабинет ученика/родителя

Показывать:

- предстоящие и прошедшие собственные занятия;
- остаток и срок действия абонемента;
- разовые оплаченные занятия;
- статус занятия: запланировано, проведено, отменено вовремя, поздняя отмена, пропуск;
- только после проведённого урока — комментарий учителя, тему, выполненное домашнее задание, новое домашнее задание и краткое описание того, как прошёл урок.

Комментарии учителя доступны только администратору, самому ученику и связанным с ним родителям.

### 4.6. Админ-панель

Администратор может:

- видеть полное расписание и имена учеников;
- добавлять, редактировать и архивировать учеников и связи с родителями;
- создавать одиночные и еженедельные уроки;
- блокировать личное время и отпуск;
- отмечать оплату вручную;
- выдавать абонемент на 4 или 8 уроков;
- добавлять отдельные оплаченные занятия;
- отмечать посещение, отмену, пропуск и списание;
- добавлять отчёт по проведённому уроку;
- видеть журнал изменений баланса и событий;
- фильтровать календарь по ученику и статусу.

## 5. Абонементы и списание

Типы продуктов:

- 4 занятия, срок действия 30 дней;
- 8 занятий, срок действия 60 дней;
- отдельно оплачиваемое разовое занятие.

Абонемент содержит дату оплаты/активации, дату окончания, исходное количество, остаток, статус и связь с учеником. По умолчанию срок начинается в момент, когда администратор отмечает оплату. Если нужна иная дата, администратор задаёт её явно.

Только администратор меняет статус оплаты, посещения и факт списания. Не списывай занятие автоматически просто после наступления времени урока.

Каждое изменение баланса хранить как неизменяемую операцию ledger: `purchase`, `lesson_debit`, `manual_credit`, `manual_debit`, `refund`. Текущее значение можно кешировать, но оно должно сверяться с журналом. Одна операция списания не может примениться дважды; используй idempotency key, связанный с уроком.

Если абонемент истёк, остаток не используется для новых броней. Исторические сведения сохраняются. Решение о переносе остатка принимает только администратор отдельной операцией.

## 6. Отмена за 4 часа

Ученик или родитель может отменить только собственный предстоящий урок. Граница рассчитывается по абсолютному времени: если до начала не менее 4 часов, статус `cancelled_on_time`, занятие не списывается или ранее зарезервированный кредит освобождается. Если осталось меньше 4 часов, статус `cancelled_late`, занятие подлежит списанию после решения/отметки администратора.

Интерфейс обязан до подтверждения явно сообщить последствие. Сервер повторно вычисляет границу; время браузера не является доверенным. Администратор может отменить урок без списания, но обязан выбрать причину. Все действия записываются в аудит.

## 8. Предлагаемая структура Firestore

Используй auto-ID, серверные timestamps и валидируй поля. Точную структуру можно улучшить, не ослабляя требования.

```text
users/{uid}
  role, displayName, email, timezone, status, createdAt

students/{studentId}
  displayName, status, ownerUid?, createdAt

studentGuardians/{linkId}
  studentId, userUid, relationship, status

availabilityRules/{ruleId}
  weekday, startLocal, endLocal, timezone, validFrom, validUntil

blockedTimes/{blockId}
  startAt, endAt, reason, createdBy

lessonSeries/{seriesId}
  studentId, weekday, localStartTime, timezone, durationMinutes,
  startsOn, endsOn, status, createdBy, createdAt

lessons/{lessonId}
  studentId, seriesId?, startAt, endAt, timezoneAtCreation,
  status, bookingType, createdBy, cancellation?, attendance?,
  debitTransactionId?, createdAt, updatedAt

lessonReports/{lessonId}
  topic, completedHomework, assignedHomework, summary,
  visibility, publishedAt, authorUid

subscriptions/{subscriptionId}
  studentId, kind, totalLessons, remainingLessons,
  paidAt, startsAt, expiresAt, status, createdBy

balanceTransactions/{transactionId}
  studentId, subscriptionId?, lessonId?, type, delta,
  idempotencyKey, reason, createdBy, createdAt

auditLogs/{logId}
  actorUid, action, entityType, entityId, before?, after?, createdAt
```

Для выборок подготовь индексы по `studentId + startAt`, `seriesId + startAt`, `status + startAt` и другим реально используемым запросам. Не загружай всю базу и не фильтруй секретные записи только на клиенте.

## 9. Безопасность и приватность

Firestore Rules должны реализовывать deny-by-default.

- `admin` имеет административный доступ в пределах приложения.
- Клиент читает собственный профиль и только уроки/отчёты/абонементы связанных учеников.
- Клиент не может менять оплату, остаток, посещение, отчёт учителя, роль или audit log.
- Клиент не может создать урок для несвязанного ученика.
- Критичные создания и изменения выполняются Functions, а прямые записи клиентом запрещены.
- Никакой пользователь не может назначить себе роль администратора.
- Не отдавать клиенту список чужих уроков для последующей маскировки; формировать доступность на сервере или через безопасную агрегированную модель.
- Валидировать типы, допустимые enum-значения, длину текста и неизменяемые поля.
- Включить App Check перед production-запуском.

Покрой правила тестами Emulator Suite: пользователь A не читает данные B; родитель читает данные связанного ребёнка; ученик не меняет остаток; неавторизованный пользователь ничего приватного не читает; admin выполняет разрешённые операции.

## 13. Пошаговая публикация для владельца без опыта

README должен содержать команды отдельно для Windows PowerShell и объяснять каждое действие.

### Локальный запуск

1. Установить Git, Node.js LTS и Firebase CLI.
2. Клонировать репозиторий.
3. Выполнить `npm ci`.
4. Скопировать `.env.example` в `.env.local` и вставить web config Firebase; `.env.local` не коммитить.
5. Запустить эмуляторы `firebase emulators:start`.
6. В другом терминале запустить `npm run dev`.
7. Запустить `npm test`, `npm run lint` и тесты правил.

### Создание Firebase-проекта

1. Открыть Firebase Console и создать проект.
2. Добавить Web App.
3. Включить Authentication → Email/Password.
4. Создать Firestore в подходящем регионе; регион после создания менять сложно.
5. Установить Firebase CLI и выполнить `firebase login`.
6. Выполнить `firebase use --add` и выбрать проект.
7. Развернуть Rules и индексы сначала в development-проект.
8. Создать администратора безопасным server-side скриптом и задать custom claim `admin`.
9. Развернуть Functions и Hosting: `firebase deploy` после успешных тестов.
10. Открыть выданный адрес `*.web.app` и пройти контрольный сценарий.

### GitHub

1. Создать приватный репозиторий на GitHub.
2. Добавить remote и отправить основную ветку.
3. Убедиться, что `.env.local`, пароли, service-account JSON и логи исключены через `.gitignore`.
4. Включить branch protection и обязательные проверки.
5. Для автоматического deploy предпочесть официальный Firebase GitHub integration или Workload Identity; не коммитить ключи.

## 14. Приёмочные сценарии

Система считается готовой, если подтверждены все сценарии:

1. Родитель входит и видит только занятия связанного ребёнка.
2. Другой родитель не может получить эти данные даже прямым запросом к Firestore.
3. Родитель выбирает свободный слот; урок сразу появляется как подтверждённый.
4. Две одновременные попытки занять один слот не создают двойную бронь.
5. Учитель создаёт еженедельную серию и удаляет один урок, не разрушая серию.
6. Учитель удаляет выбранный и последующие уроки; прошлые проведённые записи сохраняются.

14. Ученик видит опубликованный отчёт только по своему проведённому уроку.

- Все даты и операции бронирования проверяются сервером.
- Пять ключевых потоков пройдены вручную на desktop и mobile.
